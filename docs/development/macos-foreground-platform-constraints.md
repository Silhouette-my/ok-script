# ok-script macOS Foreground Platform Constraints

Status: **normative implementation constraints for the OK-WW macOS foreground MVP**

This document governs reusable platform work in `ok-script`. The companion OK-WW `MACOS_ENGINEERING_CONSTRAINTS.md` remains the normative product contract. This file may refine framework implementation but may not weaken foreground-only operation, public-API-only operation, fail-closed safety, or Windows compatibility.

## 1. Scope and ownership

`ok-script` owns reusable capabilities:

- platform-neutral desktop device routing;
- desktop window-target abstractions;
- macOS process/application/window discovery;
- ScreenCaptureKit capture;
- Quartz foreground keyboard and mouse input;
- foreground/focus guard;
- cursor and permission services;
- frame geometry and coordinate conversion;
- held-input state and `release_all()`;
- platform-conditioned dependency and import boundaries;
- capture/input lifecycle, diagnostics, and failure states.

Wuthering Waves matching hints, verified bundle identifiers, game hotkeys, tasks, assets, and user-facing game documentation belong in `ok-wuthering-waves`.

The framework must not contain game-specific shortcuts merely because OK-WW is the first macOS consumer.

## 2. Development and delivery model

- Use the long-lived `feature/macos-foreground-mvp` branch created from a recorded `upstream/master` SHA.
- `origin` points to the writable contributor fork; `upstream` points to `ok-oldking/ok-script`.
- Keep the companion OK-WW repository on the matching integration branch.
- Develop through a sibling editable install. Do not publish temporary packages, use mutable branch dependencies, or vendor either repository into the other.
- Keep commits logical, reviewable, and bisectable. Do not open foundation-only or incremental merge PRs.
- The final `ok-script` PR and OK-WW PR are one coordinated MVP delivery. The final OK-WW dependency must be immutable.
- Any deliberate constraint deviation requires an architecture decision record documenting alternatives, security/permission impact, Windows regression impact, tests, migration, and rollback.

## 3. Platform and API baseline

The first supported consumer baseline is:

- Apple Silicon arm64;
- macOS 13 or newer;
- Python 3.12 arm64 as the reference development interpreter;
- public AppKit, ScreenCaptureKit, Core Graphics/Quartz, ApplicationServices, Foundation, and CoreFoundation APIs only.

The MVP excludes:

- background or minimized automation;
- BetterDisplay and virtual displays;
- private `CGVirtualDisplay` or WindowServer interfaces;
- `CGEvent.postToPid` as background control;
- game injection, dylib injection, swizzling, Metal hooks, or anti-cheat bypasses;
- TCC modification or permission bypasses;
- root requirements.

## 4. Dependency and import boundaries

- `pyproject.toml` is the dependency source of truth.
- Windows-only packages such as `pywin32`, `pydirectinput`, `pycaw`, applicable `comtypes`, and Windows-only uses of `mouse` must use environment markers or Windows-only extras.
- macOS dependencies must use the smallest required PyObjC framework wrappers.
- Generated lock output is regenerated by tooling, not hand-edited.
- Shared modules may not unconditionally import Win32, `ctypes.windll`, `ctypes.WinDLL`, AppKit, Quartz, ScreenCaptureKit, ApplicationServices, or other platform implementations.
- Select the platform first, then lazily import the implementation.
- Do not scatter broad `try/except ImportError` blocks to conceal an incorrect boundary.
- On macOS, `import ok`, `DeviceManager`, task executor, device abstractions, and test discovery must not load Win32-only modules.
- On Windows, shared imports and tests must not require PyObjC.

## 5. Desktop target abstraction

Do not expand `HwndWindow` into a nominally generic object that exposes HWND assumptions to all platforms.

Introduce or evolve a platform-neutral desktop target that can represent:

- process identity;
- optional application or bundle identifier;
- platform window identifier;
- title/display name;
- outer and content geometry;
- capture geometry and generation;
- existence and active/frontmost state;
- activation request and observed activation;
- refresh/rebind after window recreation.

Windows should adapt existing HWND behavior with minimal change. macOS may bind `NSRunningApplication`, `SCWindow`, `CGWindowID`, and PID behind the common contract.

Consumers must not branch on whether the underlying identifier is an HWND or a `CGWindowID`.

## 6. Capture contract

Production macOS automation capture must use a persistent ScreenCaptureKit `SCStream` for the selected window, preferably through `SCContentFilter(desktopIndependentWindow:)`.

Each successful frame must be:

- `numpy.ndarray`;
- `uint8`;
- shape `(height, width, 3)`;
- BGR channel order;
- owned or otherwise immutable for the consumer lifetime;
- game content only, without cursor, title bar, border, or shadow.

Capture rules:

- publish the newest complete frame only;
- use bounded storage and allow old-frame dropping;
- never run OCR, recognition, task logic, or Qt updates in the capture callback;
- test row stride, padding, BGRA-to-BGR conversion, lifetime, and concurrent publication;
- associate every frame with a geometry/capture generation;
- invalidate old frames and coordinates immediately when resize, rebind, scale change, or fatal capture failure begins;
- handle process exit, window recreation, fullscreen/mode changes, content-size changes, display-scale changes, permission revocation, and stream stop;
- use bounded retry/backoff and explicit terminal states, not an endless tight loop.

`SCScreenshotManager`, whole-display capture, and desktop crop are diagnostic-only. They must not feed the task executor or become automatic production fallbacks.

## 7. Coordinate contract

Task and recognition coordinates are frame-local physical pixels.

Only platform backends convert them to:

- macOS logical points;
- Core Graphics global coordinates;
- Qt logical coordinates;
- any backend-specific event representation.

An input operation must use the current validated geometry generation. Retina conversion must be unit-tested for scale 1.0, 2.0, offsets, and observed non-integer assumptions where applicable. Never hardcode scale 2.0.

## 8. Foreground input contract

Production macOS input uses public Core Graphics Quartz events.

Required behavior includes:

- tap, key down, and key up;
- left/right/middle mouse down and up;
- absolute movement and click;
- scroll when required by framework consumers;
- relative/delta movement sufficient for camera control;
- explicit held-key and held-button tracking;
- idempotent `release_all()`.

Immediately before each event or short atomic batch, verify that:

- the target process/window still exists;
- the target process is alive;
- the target application is the system frontmost application.

If validation fails:

1. do not post the pending ordinary event;
2. close the input gate;
3. release tracked held state;
4. signal an explicit focus-loss/target-loss pause or stop state.

Never post first and check afterward. An atomic batch may not span sleeps, frame waits, activation, permission requests, or other focus-changing operations.

## 9. Held-state concurrency and shutdown

Ordinary input, target invalidation, task stop, and `release_all()` must share one thread-safe state boundary.

- Once invalidated, no new ordinary key, button, movement, click, scroll, or text event may cross the input gate.
- The focus-loss release path may emit only key-up/button-up events corresponding to tracked held state.
- `release_all()` must remain safe after target disappearance, continue after individual release failures, and clear all internal held state even when event posting fails.
- Task cancellation, executor stop, capture fatal error, device switch, permission revocation, target exit, and application exit all invoke safe release.
- Shutdown order is: block new input → `release_all()` → stop capture and worker threads → destroy Qt/Python objects.
- Do not rely on interpreter finalization order for safety.

Relative camera movement must remain below `hardware-validated` until tested in the official game. Combat, navigation, and route support may not be claimed before this gate passes.

## 10. Permission contract

- Use supported screen-capture preflight/request APIs.
- Use supported Accessibility trust checks and prompts.
- Missing or revoked permission is an explicit actionable state.
- Do not retry permission requests in a tight loop.
- Do not edit TCC databases or request root to bypass system controls.
- Terminal/Python permission is development-only evidence. Final permission acceptance uses a packaged application with a stable bundle identifier.

## 11. Windows regression contract

The macOS port must preserve existing:

- WGC and BitBlt selection and behavior;
- Windows interaction methods;
- HWND discovery and selection;
- public capture/interaction/task APIs;
- configuration keys;
- ADB behavior.

Prefer narrow adapters around working Windows implementations. Do not rewrite Windows paths merely for aesthetic symmetry.

## 12. Required tests and evidence

Automated tests must cover:

- platform selection and import isolation;
- desktop target behavior;
- frame format, stride, ownership, and geometry generation;
- coordinate conversion;
- held-state transitions and idempotent release;
- focus loss and target disappearance preventing subsequent input;
- shutdown and fatal capture paths invoking release;
- Windows compatibility.

CI must not require Wuthering Waves. Real-game and packaged-app results are recorded separately with commit SHA, host/macOS/game details, resolution, window mode, exact procedure, and outcome.

Use only these capability states:

1. `not-implemented`;
2. `unit-tested`;
3. `hardware-validated`;
4. `packaged-app-validated`.

Documentation, PR descriptions, UI, and release notes must not claim a higher state than the recorded evidence. A regression reopens the affected gate.
